# TEAMNOTE 개발 계획

## 현재 준비된 범위

- Java 21·Spring Boot 4.1.1·Gradle Wrapper 설정
- Web MVC·JPA·Validation·H2와 테스트 의존성
- commonmark-java·GFM Tables·jsoup의 고정 버전과 공통 Bean 설정
- 공통 성공·오류 응답 및 MVC 예외 처리
- Project·Task·Meeting Entity, 상태 enum, 기본 JpaRepository
- H2 로컬 프로필과 더미 SQL, 별도 테스트 프로필
- 계층별 폴더, 공통 설정 테스트, 실행 안내
- 프로젝트 생성 검증·등록·전체 목록·상세 API, Request·Response DTO, Service 인터페이스·구현체
- 공통 도메인 예외 3종과 400·404·409 매핑, 프로젝트·공통 예외 관련 단위 테스트

**프로젝트 등록·전체 목록·상세와 공통 도메인 예외는 구현했습니다.** [사용법과 테스트 데이터 준비 방법](PROJECT_API.md)을 참고합니다. 프로젝트 수정·삭제·조건 검색, 업무·회의 API, Markdown 처리 Service·미리보기는 앞으로 구현할 항목입니다. 아래 API 계획은 현재 구현한 기능과 남은 목표를 함께 설명합니다.

## 세 명의 담당 범위

| 담당 | 도메인 기능 | 추가 기술 적용·공통 업무 |
| --- | --- | --- |
| 팀장 | 프로젝트 CRUD, 이름·상태 조건 검색, 시작·종료일 검증, 하위 데이터가 있는 프로젝트 삭제 제한 | Markdown 처리 Service·미리보기 API, 공통 계약 유지, 통합 |
| 팀원 A | 업무 CRUD, 담당자·상태·마감일 검색, 완료 시각 관리, 프로젝트 소속 검증 | 업무 설명에 표 변환·정제 적용 및 검증, 팀원별 SQL 통합 |
| 팀원 B | 회의 CRUD, 기간 검색, 시작·종료 시각 검증, 프로젝트 소속 검증 | 회의록 변환·정제 적용 및 HTML 정책 검증, 팀원별 Postman 결과 통합 |

각자 Controller·Service 인터페이스/구현체·DTO·쿼리·예외·테스트·Postman 결과를 작성합니다. 자료 통합 담당자가 해당 자료 전체를 대신 작성하는 방식으로 분담하지 않습니다.

## API 계획

각 기본 경로에 POST 등록·GET 목록·GET `/{id}` 상세·PUT `/{id}` 수정·DELETE `/{id}` 삭제를 구현합니다.

| 담당 | 기본 경로 | 목록 검색 |
| --- | --- | --- |
| 팀장 | `/api/projects` | 이름 키워드·상태 |
| 팀원 A | `/api/projects/{projectId}/tasks` | 담당자·상태·마감일 범위·기한 초과 |
| 팀원 B | `/api/projects/{projectId}/meetings` | 회의 시작·종료 조회 기간 |

추가 공통 API: `POST /api/content/preview` — Markdown Request DTO를 받아 변환·정제한 HTML Response DTO를 반환합니다.

성공 상태는 등록 `201`, 조회·수정·삭제 `200`을 기준으로 사용합니다. 삭제도 공통 JSON 응답을 반환합니다. 입력 오류는 `400`, 없는 대상·다른 프로젝트 소속 대상은 `404`, 하위 데이터가 남은 프로젝트 삭제는 `409`로 처리합니다.

도메인별 Service는 `ProjectService`/`ProjectServiceImpl`과 같은 이름으로 분리합니다. 요청은 Request DTO, 검색은 검색 조건 DTO, 응답은 Response DTO로 작성합니다. Controller와 DTO에서 Entity를 참조하지 않습니다.

## 구현 순서

1. 각 도메인의 등록·수정·검색·응답 DTO와 Service 인터페이스를 확정합니다.
2. Entity 생성·변경 동작과 Service 비즈니스 규칙을 구현합니다.
3. 각자 조건 검색용 JPQL을 최소 1개 작성하고, 목록·상세·소속 조건을 검증합니다.
4. Controller에 POST·GET·PUT·DELETE를 연결하고 상태코드·응답 계약을 맞춥니다.
5. 공통 Markdown 처리 Service를 구현하고 세 도메인의 조회와 미리보기에 연결합니다.
6. 정상·실패 테스트, Postman 결과, 개인 주요 작업 2건 이상의 근거를 확보합니다.

프로젝트가 업무·회의를 함께 삭제하지 않도록 관계를 구성했습니다. 삭제 제한은 Service의 사전 검사와 DB 외래 키 제약을 함께 고려해 구현합니다. 프로젝트 생성의 기간 검증은 구현했으며, 수정 시 검증·업무와 회의의 소속·완료 시각·회의 시각 규칙은 아직 구현 전입니다.

## 테스트와 보고서

안내서 최소 조건은 팀 전체 자동화 테스트 3건 이상, Controller 1건 이상, Service 또는 Repository 1건 이상, 실패·예외 검증 1건 이상입니다. 채점표에는 각 테스트의 성공·실패 검증에 관한 더 강한 표현이 있으므로, 계획상 각자 다음 6건 이상을 준비합니다.

| 계층 | 정상·실패 검증 |
| --- | --- |
| Controller | 정상 등록 `201` / 잘못된 요청 `400` |
| Service | 핵심 규칙 정상 처리 / 잘못된 기간·없는 대상 등 예외 |
| Repository | 조건에 맞는 데이터 조회 / 조건 불일치·다른 프로젝트 데이터 제외 |

공통 설정 테스트만으로 수행평가 테스트를 모두 완료했다고 판단하지 않습니다. 라이브러리는 설정에 추가한 근거와 실제 기능에서 사용한 근거를 구분하고, 실제 API 응답·테스트 결과까지 보고서에 기록합니다.

개인 보고서에는 기본 정보, 서비스 소개, 팀 역할, 실행 방법, API 전체 명세·Postman 결과, 계층·JPA·DTO·예외 설계, 대표 요청 흐름, 테스트 결과, 직접 수행한 주요 구현 2건 이상, 추가 기술 선정·활용 결과, 실제 트러블슈팅·회고를 작성합니다.
